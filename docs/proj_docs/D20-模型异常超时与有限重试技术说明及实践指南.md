# D20 模型异常超时与有限重试技术说明及实践指南

## 1. 适用范围

本文说明 D20 的模型调用异常分类、Spring AI 1.1.8 重试行为、HTTP 超时层次、同步/流式差异、有限重试边界和排障实验。

适用代码：

- 同步入口：`ChatController` → `KnowledgeChatOrchestrator` → `DeepSeekAiChatService`。
- 流式入口：`ChatStreamController` → `KnowledgeChatOrchestrator` → `DeepSeekAiChatService`。
- 治理配置：`ModelCallConfiguration`、`ModelCallProperties`。
- 异常分类：`model` 包。

不适用：

- Prompt 业务纠错、JSON 修复重放。
- 断路器、限流、多模型路由。
- 真实 API 计费、账户配额管理与供应商对账。

## 2. 为什么必须核实 1.1.8

Spring AI 的默认值随版本变化。D20 没有使用当前网页最新版或较新 API 的经验值，而是检查本项目实际依赖的 1.1.8 JAR。

本地核验结果：

| 属性/实现 | 1.1.8 实际行为 |
|---|---|
| `spring.ai.retry.max-attempts` | 默认 10 |
| `spring.ai.retry.backoff.initial-interval` | 默认 2s |
| `spring.ai.retry.backoff.multiplier` | 默认 5 |
| `spring.ai.retry.backoff.max-interval` | 类默认 180s |
| `spring.ai.retry.on-client-errors` | 默认 false，普通 4xx 不重试 |
| `spring.ai.retry.on-http-codes` | 可配置可重试状态码 |
| `spring.ai.retry.exclude-on-http-codes` | 可配置排除状态码 |
| DeepSeek 自动配置 | 注入 `RetryTemplate` 与 `ResponseErrorHandler` |
| `DeepSeekChatModel.internalCall` | 同步经过 `RetryTemplate.execute` |
| `DeepSeekChatModel.internalStream` | 直连 WebClient 流，不经过 `RetryTemplate` |

证据文件：

- `docs\evidence\D20\D20-retry-configuration-metadata.json`
- `docs\evidence\D20\D20-retry-properties-defaults-javap.txt`
- `docs\evidence\D20\D20-deepseek-autoconfiguration-javap.txt`
- `docs\evidence\D20\D20-deepseek-chatmodel-javap.txt`

直接采用默认值会造成最多 10 次尝试和很长的指数退避，不符合 D20 的有限、低成本和可观测要求。

## 3. 唯一重试责任层

### 3.1 结构

```text
DeepSeekChatModel
  └─ Spring Boot 容器中的唯一 RetryTemplate
       ├─ ModelAttemptRetryPolicy
       ├─ TimeoutRetryPolicy
       ├─ ModelRetryBackOffPolicy
       └─ ModelRetryListener
```

`ModelCallConfiguration#retryTemplate` 创建该实例。DeepSeek 自动配置通过构造参数取得并注入模型。

`ApplicationContextLoadTest.deepSeekChatModelShouldUseTheSingleD20RetryTemplate` 验证模型字段中的重试模板与容器 Bean 是同一个实例。

### 3.2 为什么不在 Service 再试

如果 Spring AI、Service、HTTP 客户端和网关各重试一次，实际请求次数会相乘。D20 只允许一个责任层，底层请求次数才可计算、可测试和可观测。

`spring.ai.retry.max-attempts=1` 是防御性 fallback，正常启动时自定义 `RetryTemplate` 存在，实际使用 `app.ai.model-call.max-attempts=2`。

## 4. 超时分层

### 4.1 四类不能混用的超时

| 层次 | D20 配置 | 默认值 | 说明 |
|---|---|---:|---|
| 服务端 SSE 容器 | `app.ai.stream-timeout-ms` 与流式总时限推导 | 60s / 180s | MVC `SseEmitter` 的容器兜底，不是模型 HTTP 建连 |
| 模型 TCP 建连 | `connect-timeout` | 5s | RestClient 和 WebClient |
| 单次响应读取 | `response-timeout` | 30s | RestClient 读取、WebClient response timeout |
| 同步总 Deadline | `total-deadline` | 90s | 覆盖全部同步尝试和退避 |
| 流式总时限 | `stream-total-timeout` | 180s | 从流开始到结束的绝对上限 |
| 流式空闲 | `app.ai.stream-timeout-ms` | 60s | 首包或相邻分片最大间隔 |

### 4.2 RestClient

`deepSeekRestClientTimeoutCustomizer` 从 Spring Boot 的
`ClientHttpRequestFactoryBuilder` 创建请求工厂，并设置连接与读取超时。

Spring AI 自动配置使用 Boot 提供的 `RestClient.Builder`，因此 Customizer 实际进入同步模型 HTTP 调用。

### 4.3 WebClient

`deepSeekWebClientTimeoutCustomizer` 使用 Reactor Netty：

- `CONNECT_TIMEOUT_MILLIS`：建连超时。
- `responseTimeout`：响应超时。

子模块显式添加 `reactor-netty-http`，否则当前 Spring AI starter 只传递 WebFlux API 而没有可运行连接器。

### 4.4 预算公式

```text
最坏同步耗时
= maxAttempts * (connectTimeout + responseTimeout)
  + (maxAttempts - 1) * maxBackoff
```

默认：

```text
2 * (5s + 30s) + 1 * 10s = 80s
```

配置校验要求 `totalDeadline >= 80s`。默认 90s 留出 10s 余量。

该公式无法证明单次请求一定在 `connect+response` 内结束；它约束的是配置上界。同步总 Deadline 在重试循环边界检查，不会强制中断正在执行的线程。因此必须同时保留单次 HTTP 超时。

### 4.5 流式双层时限

```java
outcome.chunks()
    .timeout(Duration.ofMillis(streamTimeoutMs))
    .takeUntilOther(Mono.delay(streamTotalTimeout)
        .flatMap(ignored -> Mono.error(TimeoutException::new)));
```

第一层抑制“长时间无分片”，第二层抑制“持续小分片导致永不完结”。

SSE 容器超时取两个时限较大值再加 5s 收尾宽限；应用层先结束并由回调取消上游订阅。

## 5. 内部异常模型

### 5.1 分类对象

`ModelFailure` 只包含：

- `category`
- `httpStatus`
- `retryable`
- `retryAfter`

它不包含 Prompt、用户消息、模型响应正文、API Key、请求头或堆栈文本。

### 5.2 分类边界

分类器按以下优先级识别：

1. D20 自定义可重试/不可重试异常。
2. 本地 AI 配置异常。
3. WebClient/RestClient 的 HTTP 状态异常。
4. 网络根因：DNS、SSL、建连、读取超时、取消。
5. 应用级取消与 Deadline。
6. JSON/Spring AI 异常。
7. 其他 I/O 与未知异常。

对网络异常使用 cause 链，不依赖包装异常的最外层类型。这样可区分
`ResourceAccessException` 内部的 `SocketTimeoutException` 与 `ConnectException`。

### 5.3 HTTP 状态策略

| 状态 | 分类 | 默认重试 | 理由 |
|---:|---|---:|---|
| 400/422 | 参数错误 | 否 | 重发不会修正请求 |
| 401 | 鉴权失败 | 否 | 凭据不会自行恢复 |
| 402 | 永久额度 | 否 | 需充值/配置 |
| 403 | 授权失败 | 否 | 权限不会立即恢复 |
| 404 | 模型/资源不存在 | 否 | 配置错误 |
| 408 | 读取/请求超时 | 否 | 结果可能不确定 |
| 409 | 业务拒绝/冲突 | 否 | 请求语义问题 |
| 429 | 可恢复限流 | 条件是 | 尊重 Retry-After 与预算 |
| 502/503/504 | 临时上游不可用 | 是 | 常见可恢复状态 |
| 其他 5xx | 上游错误 | 否 | 当前仅批准三项明确状态 |

未批准的状态即使属于 5xx 也不重试，以避免“所有 5xx 都重试”扩散。

### 5.4 永久额度识别

同步错误处理读取 HTTP 响应正文用于分类。以下标记视为永久额度/余额问题：

- `insufficient_quota`
- `quota_exceeded`
- `billing_hard_limit`
- `insufficient balance`
- `余额不足`
- `额度不足`

正文只在当前分类调用内使用，不写入异常消息、日志或客户端响应。

## 6. 对外错误映射

| 对外码 | 提示语义 | 常见分类 |
|---:|---|---|
| 4001 | 请求参数校验失败 | Controller/DTO 校验、长度错误 |
| 5001 | AI 配置或鉴权异常 | 参数、鉴权、授权、模型不存在、永久额度 |
| 5002 | AI 服务暂不可用 | 限流、5xx、建连、读取超时、网络 I/O |
| 5000 | 系统繁忙 | Deadline、解析失败、取消、未知 |

同步接口仍由 `GlobalExceptionHandler` 返回 `Result{code,msg,data}`，HTTP 层为 200。

流式响应开始后不能改成 JSON。异常通过 SSE `error` 事件返回，事件后关闭，不发送 `complete`。

## 7. 有限重试算法

### 7.1 尝试次数

`SimpleRetryPolicy(maxAttempts)` 和分类判断组合。默认：

```text
首次调用 + 1 次重试 = 2 次总尝试
```

不是“再试 2 次后共 3 次”。

### 7.2 退避

第 n 次失败的基础等待：

```text
initialBackoff * 2^(n-1)
```

再加入 `jitter-factor` 范围内的随机抖动，最后截断到 `max-backoff`。

默认序列为 500ms、1s、2s……但总尝试数只有 2，实际正常只会使用一次退避。

### 7.3 Retry-After

支持：

- 非负整数秒。
- RFC 1123 HTTP 日期。

等待值取“指数退避”和“Retry-After”的较大值，再受 `max-backoff` 限制。若 `Retry-After` 超过 `max-backoff`，分类器直接不批准重试，不先等待再发现超预算。

### 7.4 总 Deadline

`CompositeRetryPolicy` 同时要求：

- 分类批准且未超过尝试次数。
- 总 Deadline 未耗尽。

退避发生前后，重试循环都会检查剩余预算。

## 8. 同步与流式差异

| 维度 | 同步 | 流式 |
|---|---|---|
| 底层客户端 | RestClient | WebClient |
| Spring AI 路径 | `internalCall` | `internalStream` |
| 是否经过 RetryTemplate | 是 | 否 |
| D20 自动重试 | 最多 2 次 | 否 |
| 连接超时 | 生效 | 生效 |
| 响应超时 | 单次读取超时 | WebClient 响应超时 |
| 总时限 | RetryTemplate 总预算 | Reactor 绝对时限 |
| 客户端取消 | 中断当前调用 | 取消上游订阅 |
| 已输出后重放 | 不适用 | 禁止 |

### 8.1 流式首内容前

即使尚未向浏览器发送答案分片，传输可能已经由上游开始处理。为了保守控制重复计费和重复内容，D20 对流式失败不自动重试。

测试 `ChatStreamErrorEventTest.errorAfterStreamStartedShouldEmitErrorEventWithoutComplete`
验证服务只调用一次，并返回 SSE `error`。

### 8.2 流式首内容后

测试 `failureAfterFirstDeltaShouldNotReplayFromBeginning` 验证：

- 第一个 `delta` 已发送。
- 后续错误产生 `error`。
- 不出现 `complete`。
- 模型流式调用只发生一次。

### 8.3 客户端断开

`StreamClientDisconnectIntegrationTest` 验证断开后：

- 取消上游订阅。
- 不写入正常 `COMPLETED` 终态。
- 有部分答案时保留 `INTERRUPTED`。
- 没有答案时标记 `FAILED`。

## 9. 结果不确定性与成本风险

HTTP 重试并非天然幂等。典型状态：

| 场景 | 请求是否可能已处理 | D20 选择 |
|---|---|---|
| 连接拒绝 | 否 | 可有限重试 |
| 明确建连超时 | 通常否，但网络路径仍可能复杂 | 保守有限重试 |
| 请求后读取超时 | 是 | 不重试 |
| 502/503/504 | 视网关行为可能已处理 | 仅明确状态有限重试 |
| 429 | 通常未处理或未完成生成 | 条件重试 |
| 流中断 | 可能已处理并已计费 | 不重试 |

当前没有业务幂等键、供应商请求 ID 对账或“结果查询”接口，因此不能证明请求后超时重试安全。

## 10. 日志与可观测性

`ModelRetryListener` 记录：

```text
category
httpStatus
attempt
retryable
```

流式日志记录：

- requestId
- 公开业务错误码
- 分类
- 超时阈值

禁止记录：

- API Key 或 Authorization 头。
- 完整 Prompt/用户输入。
- 完整模型响应。
- 上游原始报文或堆栈到客户端。

模型默认“次数”字段是 RetryContext 的重试计数，首次调用为 0；不会跨请求共享。

## 11. 配置操作

### 11.1 默认配置

```yaml
app:
  ai:
    model-call:
      connect-timeout: 5s
      response-timeout: 30s
      total-deadline: 90s
      stream-total-timeout: 180s
      max-attempts: 2
      initial-backoff: 500ms
      max-backoff: 10s
      jitter-factor: 0.2
```

### 11.2 环境变量

| 环境变量 | 对应配置 |
|---|---|
| `AI_MODEL_CONNECT_TIMEOUT` | `connect-timeout` |
| `AI_MODEL_RESPONSE_TIMEOUT` | `response-timeout` |
| `AI_MODEL_TOTAL_DEADLINE` | `total-deadline` |
| `AI_MODEL_STREAM_TOTAL_TIMEOUT` | `stream-total-timeout` |
| `AI_MODEL_MAX_ATTEMPTS` | `max-attempts` |
| `AI_MODEL_INITIAL_BACKOFF` | `initial-backoff` |
| `AI_MODEL_MAX_BACKOFF` | `max-backoff` |
| `AI_MODEL_BACKOFF_JITTER` | `jitter-factor` |

### 11.3 校验规则

- 所有超时为正。
- `initial-backoff > 0` 且 `<= max-backoff`。
- `max-attempts` 为 1–3。
- `jitter-factor` 为 0.0–0.8。
- 总 Deadline 覆盖配置上的最坏尝试与退避。

配置不支持热更新，修改后重启应用。

## 13. 排障流程

### 13.1 先判断模式和接口

1. 检查 `app.ai.mode`/`AI_MODE`。
2. 检查同步 `/chat` 还是流式 `/chat/stream`。
3. 检查 requestId。
4. 查看日志中的 category、status、attempt、retryable。

### 13.2 判断是否真的重试

不要只看异常类型。并发、代理和网关都可能重复请求；应结合：

- Mock Server 请求计数。
- 模型调用日志 attempt。
- 网关访问日志。
- 总耗时和返回状态。

### 13.3 判断读取超时还是建连失败

查看 cause 链：

- `ConnectException`、`NoRouteToHostException`、`ConnectTimeoutException`：建连方向。
- `SocketTimeoutException`、Netty `ReadTimeoutException`、`HttpTimeoutException`：读取/响应方向。
- `UnknownHostException`、`SSLHandshakeException`：配置/安全方向，不重试。

不要把所有 `ResourceAccessException` 直接视为可重试。

### 13.4 检查 Retry-After

- 秒数形式。
- HTTP 日期形式。
- 是否超过 `max-backoff`。
- 当前总 Deadline 是否允许完整等待。

## 14. 安全实践

1. 真实 Key 只通过进程环境或程序参数注入。
2. 不把真实 Key 写入 YAML、脚本、日志、测试报告、数据库或 Git。
3. 测试 JVM 固定覆盖为无效占位值，防止宿主环境真实 Key 进入测试痕迹。
4. 不记录完整 Prompt 和模型原始响应。
5. 上游错误正文只用于必要分类，不进入异常消息。
6. SSE 客户端断开后不重试、不把半截答案标记为成功。

## 15. 已验证与未验证

### 已验证

- Spring AI 1.1.8 默认值、自动配置接线和同步/流式差异。
- RestClient/WebClient 超时实际生效。
- 429、503、永久额度、建连失败、读取超时的真实请求次数。
- 2 次总尝试、Retry-After、退避与配置预算。
- 并发请求不共享重试计数。
- 流式无重放、断开取消和总时限。
- 全量回归 161 个测试无失败。

### 未验证

- 真实 DeepSeek API 在线烟雾测试。
- 真实供应商所有限流响应正文与 `Retry-After` 格式。
- 企业代理/网关是否额外重试。
- 生产 SLA 下的超时调优。

未验证项不能写成已通过，真实调用应由获得明确授权的独立流程执行，并记录费用与请求元数据。
