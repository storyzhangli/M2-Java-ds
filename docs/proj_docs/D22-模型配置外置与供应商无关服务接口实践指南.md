# D22 模型配置外置与供应商无关服务接口实践指南

## 1. 为什么需要外置与隔离

将模型名、URL、Key 和模式散落在 Controller、Service 和供应商配置中会导致：

- 更换模型或网关必须改代码。
- 调试环境与部署环境的配置来源不一致。
- API Key 容易进入日志、源码或提交记录。
- Mock 模式被迫依赖伪造 Key。
- 未来增加其他 Provider 时，Controller/业务服务必须跟着改。

D22 将应用配置和 Provider 实现拆成两个边界：

```text
应用层
  Controller / DTO / AiChatService
        │
        ▼
Provider Adapter
  DeepSeekAiChatService
        │
        ▼
Provider Bean 配置
  DeepSeekChatModelConfiguration
        │
        ▼
Spring AI 1.1.8 DeepSeekChatModel
```

应用层不知道 DeepSeek DTO/Options。

## 2. 配置事实

### 2.1 Spring AI 1.1.8 默认自动配置

官方 DeepSeek Starter 自动配置使用：

```text
spring.ai.deepseek.api-key
spring.ai.deepseek.base-url
spring.ai.deepseek.chat.options.model
spring.ai.deepseek.chat.options.temperature
```

实际 1.1.8 字节码在构造 DeepSeekApi 前执行：

```java
Assert.hasText(apiKey, "DeepSeek API key must be set");
```

因此供应商自动配置不能接受真正空 Key；即使用 Mock 模式，也会在上下文启动时失败。

### 2.2 D22 的项目映射

应用只读取：

```text
app.ai.mode
app.ai.model
app.ai.base-url
app.ai.api-key
app.ai.temperature
app.ai.thinking.reasoner-model
```

环境变量：

```text
AI_MODE
AI_MODEL
AI_BASE_URL
AI_API_KEY
AI_TEMPERATURE
AI_REASONER_MODEL
```

实际 Bean：

```text
DeepSeekChatModelConfiguration
  -> DeepSeekApi(baseUrl, apiKey, timeout clients, error handler)
  -> DeepSeekChatOptions(model, temperature)
  -> DeepSeekChatModel(retry, tool manager, observation)
```

配置不是“只写 YAML”：`DeepSeekConfigurationBindingTest` 使用自定义 model/URL/temperature 实际创建模型并断言 Options。

## 3. 为什么禁用供应商自动配置

D22 需要在 Mock 模式无 Key 启动，而供应商自动配置对 Key 必填。采用以下条件：

1. `spring.autoconfigure.exclude` 禁用 `DeepSeekChatAutoConfiguration`。
2. 自定义 Provider Bean 只在 `app.ai.mode=deepseek` 启用。
3. 自定义 Bean 带 `@ConditionalOnMissingBean(ChatModel.class)`，允许测试或未来自定义模型覆盖。
4. Mock 模式没有模型 Bean，Mock Service 无字段依赖。
5. 真实模式在构造 Bean 前检查非空 Key。

这一方案没有引入第二个 AI 框架，也没有复制重试/异常/Trace 逻辑。

## 4. 配置优先级与启动行为

优先级：

```text
命令行参数
 > 环境变量
 > Profile 配置
 > application.yml
 > 默认值
```

启动时绑定，不热更新。

### 4.1 Mock

```text
AI_MODE=mock
AI_API_KEY=
```

结果：

- ApplicationContext 正常启动。
- 只有 MockAiChatService。
- 没有 ChatModel。
- 不发外部请求。

### 4.2 DeepSeek

```text
AI_MODE=deepseek
AI_MODEL=<模型名>
AI_BASE_URL=<HTTPS Base URL>
AI_API_KEY=<安全注入>
```

结果：

- 创建唯一 DeepSeekChatModel。
- DeepSeekAiChatService 装配。
- 不自动访问网络；实际请求仅在聊天调用时发生。

### 4.3 错误

| 错误 | 行为 |
|---|---|
| 未知 mode | 配置绑定校验失败 |
| model 空白 | 配置绑定校验失败 |
| URL 非 http/https、无 host、带 user-info | 配置绑定校验失败 |
| deepseek 但无 Key | 生产 Bean 构造失败；测试 Mock 场景 Service 返回 5001 |
| 无 Key 但 Mock | 正常 |

## 5. 服务契约与 Provider 隔离

### 5.1 AiChatService

`AiChatService` 是应用 Port：

- `chat(...)` 返回 `ChatReplyResponse`/`AiChatResult`。
- `streamChat(...)` 返回 `Flux<String>`/`Flux<StreamChunk>`。
- 参数使用 `ChatInvocation`、`ThinkingSettings`。

没有：

- `DeepSeekChatOptions`
- `DeepSeekApi`
- `DeepSeekAssistantMessage`
- provider response DTO

### 5.2 Provider 类型允许位置

`ProviderIsolationTest` 允许 DeepSeek import 仅出现在：

```text
config/DeepSeekChatModelConfiguration.java
service/DeepSeekAiChatService.java
```

Controller、DTO、`AiChatService` 和知识编排器不得引用 provider 配置。

### 5.3 调用流程

同步：

```text
Controller
 -> AiChatService
 -> DeepSeekAiChatService
 -> ChatModel.call
 -> AiChatResult
```

流式：

```text
Controller
 -> AiChatService.streamChat
 -> DeepSeekAiChatService
 -> ChatClient.stream().chatResponse()
 -> StreamChunk
 -> SseEmitter
```

业务层只看到项目内部流式分片。

## 6. DeepSeek 适配边界

DeepSeekAiChatService 内部负责：

- 项目消息 -> Spring AI `Message`
- 项目 thinking 设置 -> DeepSeek 模型选择
- `DeepSeekAssistantMessage` reasoning 提取
- DeepSeekChatOptions 模型覆盖
- ChatResponse -> 项目 AiChatResult/StreamChunk

这些转换不能向上泄漏。

## 7. 现有能力复用

D22 没有重写：

- D20 超时和唯一 RetryTemplate。
- D20 异常分类/有限重试。
- D21 TraceId/MDC。
- D21 `MODEL_CALL` 脱敏日志。
- 延迟和 Provider usage。

自定义 DeepSeek Bean 明确注入既有 `RetryTemplate` 和 `ResponseErrorHandler`。测试继续验证同步/流式与断流行为。

## 8. API Key 安全

### 8.1 允许

- OS secret manager
- CI Secret
- IDEA Environment Variables/Password source
- 临时进程环境变量

### 8.2 禁止

- `application.yml` 硬编码
- 提交 `application-local.yml`
- 测试快照
- 日志
- `.env` 自动加载假设

`app.ai.api-key` 默认空值。`AiProperties` 的 `toString()` 排除该字段。

不把 Key 拼接进异常消息；只提示环境变量名称。

## 9. Base URL 安全

只从受信任配置读取，不从用户请求动态指定。

校验：

- scheme 必须 http/https。
- host 非空。
- 不允许 `user:password@host`。

只允许配置来源，不能阻止部署者配置内部网关，因此不强制公网域名；生产审批应限制网关白名单。

## 12. 常见问题

### 修改 AI_MODEL 后接口模型名没变

检查：

1. 是否重启应用。配置不支持热更新。
2. 是否设置了命令行/更高优先级覆盖。
3. 是否仍设置旧 `DEEPSEEK_MODEL`；D22 不再读取该变量。

### Key 在 Mock 下为空仍启动

这是正确行为。Mock 无模型 Bean。

### DeepSeek 模式启动提示缺少 Key

设置 `AI_API_KEY`。不要把值写入 YAML 或 Git。

### 自定义 URL 无法启动

检查 http/https、host、user-info；不接受 `file:` 或带凭据 URL。

### Controller 看不到 DeepSeek 类型

这是设计目标。Provider DTO 必须留在 Adapter。

## 13. 扩展新 Provider

未来增加 Provider 时：

1. 新增 provider-specific `ChatModel` 配置/Adapter。
2. 实现同一 `AiChatService` 内部契约。
3. 增加应用级 provider/mode 选择。
4. 业务 Controller、DTO、Orchestrator 不改。
5. 复用超时、重试、Trace、usage 边界。

本轮没有实现第二家 Provider，也没有创建抽象工厂/注册中心。
