# D21 聊天调用可观测性技术说明与实践指南

## 1. 设计目标

D21 解决四个可观测性问题：

1. 一个聊天请求如何关联到其模型调用。
2. 模型调用日志如何在不泄露 Prompt/Completion 的前提下保留诊断价值。
3. 请求与模型延迟如何区分。
4. 只有 Provider 实际返回 Token usage 时如何记录，缺失时如何避免伪造。

实现不引入数据库、监控后端或新的分布式追踪框架。

## 2. TraceId、requestId 与 W3C Trace

### 2.1 本项目采用哪种语义

当前项目没有 Actuator、Micrometer Tracing Bridge 或 Tracer Bean。因此 D21 的 `traceId` 是：

> 一次 HTTP 请求及其模型调用的本地关联 ID

它不是跨线程池、跨服务自动传播的 W3C `traceparent`，也不提供 span 树和跨服务采样。

### 2.2 复用现有 ID

`TraceIdFilter` 原有 `X-Request-Id` 和 MDC `requestId` 已能贯穿过滤器、Controller 和业务日志，因此复用为同一 TraceId，不创建第二个独立关联维度。

响应同时返回：

```text
X-Request-Id: <id>
X-Trace-Id:   <id>
```

SSE `start.requestId` 仍保持原字段。

### 2.3 Header 校验

接受规则：

```regex
[A-Za-z0-9][A-Za-z0-9_-]{0,63}
```

默认长度上限 64，可配置为 8–128。

无效或恶意 Header：

- 不删除危险字符后继续使用。
- 不信任换行、NUL、超长字符串。
- 生成 32 位无横线 UUID。

响应只写回合法 ID，避免日志注入和伪造链路。

### 2.4 异步流

不能假定 Reactor 回调线程拥有 HTTP 请求线程的 MDC。D21 在创建模型流时捕获：

```java
String traceId = TraceIdFilter.currentTraceId();
```

后续 `doOnNext`、`doOnComplete`、`doOnError`、`doFinally` 使用局部捕获值。写 `MODEL_CALL` 时临时设置该 TraceId 供日志前缀使用，并在 finally 恢复线程原状态。

## 3. Trace 与日志关闭开关

`app.access-log.enabled` 现在只控制：

- HTTP 请求/响应正文日志过滤器。
- Controller AOP 日志。

它不再关闭 `TraceIdFilter`。因此即使正文访问日志关闭：

- Response Header 仍有 TraceId。
- SSE start 仍有 requestId。
- 模型调用仍产生 `MODEL_CALL`。

该行为由 `TraceIdWithoutAccessLogTest` 验证。

## 4. 模型调用生命周期

### 4.1 同步

```text
创建 Call（开始时间/单调时钟/TraceId）
 -> chatModel.call
 -> 观察 ChatResponse metadata
 -> 提取 usage/response id
 -> 成功或异常
 -> 写唯一终态记录
```

### 4.2 流式

```text
请求线程捕获 TraceId
 -> Flux.defer：订阅时才创建 Call
 -> ChatClient.stream().chatResponse()
 -> 每个 chunk 更新最新 usage 快照
 -> 首个非空 text/reasoning 记录 firstChunkLatencyMs
 -> onComplete / onError / cancel
 -> 写唯一终态记录
```

### 4.3 终态定义

| 事件 | status |
|---|---|
| `onComplete` | `SUCCESS` |
| 上游 `onError` | `ERROR` |
| 客户端断开/下游取消/Controller 取消订阅 | `CANCELLED` |

流式调用一旦取消，不自动重试或从头重放。模型调用记录只描述该逻辑模型调用，不把 Controller 的持久化错误伪装成模型失败。

## 5. 日志白名单

`MODEL_CALL` 不接受任意业务对象，而是逐字段构造：

```text
traceId, callId, provider, model, callMode,
startedAt, finishedAt, elapsedMs, status,
errorType, firstChunkLatencyMs,
providerResponseId,
usageStatus, usageSource,
promptTokens, completionTokens, totalTokens, totalTokensDerived
```

安全策略：

- 异常只记录类简单名，不记录 message。
- Provider response ID 只接受不超过 128 位的安全字符。
- Token 缺失字段直接省略。
- Prompt、Completion、推理文本不进入调用记录。

### 5.1 通用访问日志

原有访问日志可能记录请求/响应体。D21 增加精确敏感字段：

```text
message
prompt
completion
content
reasoningcontent
reasoning_content
```

匹配方式为字段名精确匹配，避免把 `contentType` 误脱敏。

Authorization、Cookie 等 Header 仍由既有 Header 黑名单整体掩码。

Controller 异常日志不再包含原始 `ex.getMessage()`，只保留异常类型。

## 6. Spring AI 1.1.8 Usage

### 6.1 API

本地 1.1.8 JAR：

```java
Usage.getPromptTokens(): Integer
Usage.getCompletionTokens(): Integer
Usage.getTotalTokens(): Integer
ChatResponseMetadata.getUsage(): Usage
```

三个字段均可能为 null。

### 6.2 EmptyUsage

`ChatResponseMetadata` 默认持有一个 `EmptyUsage`。该占位实现可能使 `getTotalTokens()` 等返回 0，但这不是 Provider 返回的 0。

D21 显式识别 `org.springframework.ai.chat.metadata.EmptyUsage` 并标记：

```text
usageStatus = NOT_RETURNED
usageSource = NONE
```

不输出 token 数值。

### 6.3 DefaultUsage 与 total

`DefaultUsage` 可能自行计算 total。D21：

1. 优先读取 Provider native usage 的 `totalTokens()`/`getTotalTokens()`。
2. 对无法确认来源的 `DefaultUsage.totalTokens` 不作为 Provider 原值。
3. prompt 与 completion 都明确时，允许相加，并记录：

```text
usageSource = DERIVED
totalTokensDerived = true
```

### 6.4 DeepSeek 流式

1.1.8 DeepSeek 适配器：

- 从 `DeepSeekApi.Usage` 创建带 native usage 的 `DefaultUsage`。
- 流式通过 `UsageCalculator.getCumulativeUsage` 把累计 usage附着到 `ChatResponse`。

因此每个后续 chunk 的 usage 可能是累计值。D21 使用“最新非空快照”，而不是逐 chunk 相加。

## 7. Usage 状态语义

| 状态 | prompt | completion | total | 场景 |
|---|---|---|---|---|
| `AVAILABLE` | 有 | 有 | 有/可派生 | 完整 usage |
| `PARTIAL` | 可能缺 | 可能缺 | 可能缺 | Provider 只返回部分字段 |
| `NOT_RETURNED` | null | null | null | 未返回/EmptyUsage |
| `NOT_SUPPORTED` | null | null | null | Mock/确定性链路 |

`DERIVED` 只表示 total 是允许规则下的派生值，不表示 prompt/completion 是估算值。

禁止：

- 字符数换算 token。
- 本地 tokenizer 冒充 Provider usage。
- 缺字段填 0。
- mock 模式下写伪 usage。
- 把多个累计 chunk 再相加。

## 8. 延迟语义

### 8.1 HTTP 延迟

访问日志：

```text
event = HTTP_RESPONSE
elapsedMs = 完整 HTTP 生命周期
```

### 8.2 模型调用延迟

`MODEL_CALL.elapsedMs`：

- 同步：外部模型调用的完整同步耗时。
- 流式：订阅开始到完成/错误/取消。
- 包含重试、网络等待、模型生成和流结束等待。

### 8.3 首 Chunk

`firstChunkLatencyMs` 只在首个非空 text/reasoning 输出到达时记录。

它不是：

- 连接建立时间。
- 第一个空 metadata chunk 的时间。
- 浏览器收到 SSE 的时间。

若 Provider 从未产生非空输出，就不记录该字段。

## 11. 实际排查步骤

### 11.1 请求与模型记录对不上

1. 从响应头读取 `X-Request-Id`/`X-Trace-Id`。
2. 在 `d21-access.log` 搜索该值。
3. 检查 `MODEL_CALL.traceId` 是否相同。
4. 检查 SSE `start.requestId` 是否相同。

### 11.2 流式日志前缀为空

以 `MODEL_CALL` JSON 内的 `traceId` 为准。若未来启用 Micrometer Tracing，应配置 Reactor context propagation，不要只修补 ThreadLocal。

### 11.3 看不到 token

先看 `usageStatus`：

- `NOT_SUPPORTED`：Mock 模式，正常。
- `NOT_RETURNED`：Provider 未返回或实现未提供。
- `PARTIAL`：只有部分字段。
- `AVAILABLE`：应检查相应字段。

不要用日志消息长度推断缺失 token。

### 11.4 total 为什么是派生

`totalTokensDerived=true` 表示 prompt+completion 来自 Provider，而 total 由 D21 按规则相加。若 Provider 明确给出 total，则使用 native total 且不标派生。

### 11.5 为什么没有 `completion` 文本

D21 有意不在调用记录和通用访问日志中记录 Completion。需要正文是否正确时，应通过受控调试流程，不在默认日志中放开原文。

## 12. 安全注意事项

- 真实 DeepSeek Key 仅通过环境变量/程序参数注入。
- 不写配置、不提交、不写日志。
- 测试固定使用无效占位 Key。
- 不在日志中输出 Authorization/Cookie。
- 不记录完整 Prompt/Completion。
- `traceId` 不作为 metrics 高基数标签。
- Provider response ID 仅在安全格式下记录。

## 13. 已验证、未验证与不适用

### 已验证

- Spring AI 1.1.8 Usage API 和 DeepSeek 累计 usage 路径。
- 无 tracing 依赖，当前 TraceId 是本地关联 ID。
- 同步/流式 Trace 关联。
- 恶意 Header 重新生成。
- 同步成功/错误、流式成功/错误/断流取消的单终态记录。
- 完整/部分/缺失/0/派生 usage，以及缺失不补 0。
- 访问日志关闭时 TraceId 仍可用。
- 174 项全量测试通过。

### 未验证

- 真实 DeepSeek 本轮是否返回 usage。
- 真实生产代理是否传播或覆盖 `X-Trace-Id`。
- W3C traceparent 互操作。

### 不适用

- 本轮不新增 span、采样和跨服务 Trace。
- 本轮不持久化调用记录到数据库。
