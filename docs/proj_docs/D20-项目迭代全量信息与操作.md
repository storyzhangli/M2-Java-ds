## 5. 关键设计决定

### 5.1 唯一重试责任层

DeepSeek 1.1.8 自动配置会把 Spring 容器中的 `RetryTemplate` 注入 `DeepSeekChatModel`。D20 提供唯一一个自定义 `RetryTemplate` Bean，并让自动配置使用它。

同步调用只有该层重试；Service、Controller、HTTP 客户端和应用网关都没有新增重试循环。`spring.ai.retry.max-attempts=1` 仅作为自定义 Bean 意外缺失时的安全 fallback，不是正常路径。

### 5.2 保守重试

同步最多 2 次总尝试：

- 429：可恢复限流，尊重 `Retry-After`，且退避不得超过配置上限与总 Deadline。
- 502、503、504：可恢复上游不可用，有限重试。
- 连接拒绝、无路由、明确建连超时：仅在可确认请求尚未成功发送时有限重试。
- 400、401、402、403、404、408、409、422 等客户端/永久问题：不重试。
- 永久额度耗尽、余额不足：不重试。
- 请求发出后的读取/响应超时：结果不确定，默认不重试，避免重复计费。
- DNS/SSL 配置或握手机制问题、未知异常、取消：不重试。

### 5.3 流式安全

1.1.8 的流式路径不经过 `RetryTemplate`。D20 不额外增加流式重试：

- 首内容发出前失败：直接发出 SSE `error`，不再调用第二次流。
- 已发出任意内容后失败：只结束当前错误流，不从头重放，也不拼接重复答案。
- 客户端取消/断开：停止上游订阅，按已有内容保存为 `INTERRUPTED`，否则保存为 `FAILED`。
- 流式总时限和空闲时限会主动结束上游订阅。

### 5.4 对外契约

同步接口仍为：

- URL：`POST /api/v1/ai/chat`
- HTTP 层成功处理仍返回 HTTP 200。
- 响应结构仍为 `code/msg/data`。
- 既有业务错误码仍由 `ResultCode` 表达。

流式接口仍为：

- URL：`POST /api/v1/ai/chat/stream`
- Content-Type：`text/event-stream;charset=UTF-8`
- 既有事件：`start`、`thinking`、`delta`、`citations`、`complete`、`error`

错误事件不包含上游原始报文、堆栈或凭据。

## 7. 配置说明

配置前缀：`app.ai.model-call`

| 配置 | 默认值 | 单位/含义 | 上限或约束 | 热更新 | 验证 |
|---|---:|---|---|---|---|
| `connect-timeout` | `5s` | TCP 建连超时 | 必须大于 0 | 否 | `ModelHttpClientTimeoutTest` |
| `response-timeout` | `30s` | 单次 HTTP 响应读取超时 | 必须大于 0 | 否 | RestClient/WebClient 本地慢服务测试 |
| `total-deadline` | `90s` | 同步全部尝试与退避的总预算 | 必须覆盖最坏预算 | 否 | `ModelCallPropertiesValidationTest` |
| `stream-total-timeout` | `180s` | 整个 SSE 流的总时限 | 必须大于 0 | 否 | `ChatStreamTotalDeadlineTest` |
| `max-attempts` | `2` | 同步总尝试次数，首次也计数 | 1–3 | 否 | 策略与 HTTP 集成测试 |
| `initial-backoff` | `500ms` | 首次退避 | 大于 0 且不大于 `max-backoff` | 否 | 配置边界测试 |
| `max-backoff` | `10s` | 单次退避上限 | 大于 0 | 否 | 429/退避测试 |
| `jitter-factor` | `0.2` | 指数退避随机抖动比例 | 0.0–0.8 | 否 | 配置绑定/策略测试 |

既有流式空闲/首包超时仍为：

| 配置 | 默认值 | 作用 |
|---|---:|---|
| `app.ai.stream-timeout-ms` | `60000` | 首个及相邻流分片的最大空闲间隔 |

默认同步最坏预算：

```text
maxAttempts * (connectTimeout + responseTimeout)
  + (maxAttempts - 1) * maxBackoff
= 2 * (5s + 30s) + 10s
= 80s
< totalDeadline 90s
```

非法组合会在配置绑定阶段拒绝启动。

## 9. Spring AI 1.1.8 核验结论

本地 1.1.8 JAR 证据确认：

- `spring.ai.retry.max-attempts` 默认 10。
- 初始退避默认 2000ms，multiplier 默认 5，最大间隔类默认 180000ms。
- `spring.ai.retry.on-client-errors` 默认 false。
- 默认可用属性包括 `on-http-codes` 与 `exclude-on-http-codes`。
- DeepSeek 自动配置接收 `RetryTemplate` 和 `ResponseErrorHandler`。
- 同步 `internalCall` 调用 `RetryTemplate.execute`。
- 流式 `internalStream` 不经过这个 `RetryTemplate`。

默认 Spring AI 策略不能完成 D20 所需的以下判断：

- 区分请求发送前建连失败与请求发送后读取超时。
- 解析供应商 `Retry-After`。
- 识别永久额度正文。
- 对所有尝试和退避施加统一业务 Deadline。
- 在流式首段后禁止重放。

因此 D20 覆盖自动配置的 `RetryTemplate` 与 `ResponseErrorHandler`，没有叠加第二层重试。

## 12. 故障排查

### 应用拒绝启动并提示 Deadline 不足

重新计算：

```text
总 Deadline >= maxAttempts * (connectTimeout + responseTimeout)
              + (maxAttempts - 1) * maxBackoff
```

不要为了启动而关闭校验；应调整超时预算或重试次数。

### 503 只看到一次请求

依次检查：

1. 是否处于 `deepseek` 模式。
2. 标准错误是否属于分类器批准的重试类型。
3. `Retry-After` 是否超过 `max-backoff`。
4. 总 Deadline 是否已耗尽。
5. 日志中的 `category` 与 `attempt`。

### 429 长时间不重试

检查 `Retry-After` 是否超过 `max-backoff`。超过时系统保守地停止重试，避免超出预算。

### 请求后超时没有重试

这是设计行为。请求可能已被上游处理，响应丢失时重试可能重复计费。

### SSE 首段后报错

这是正确的失败收口。客户端应保留已展示内容并提示未完整完成，不应自动重新请求并拼接旧/新答案。
