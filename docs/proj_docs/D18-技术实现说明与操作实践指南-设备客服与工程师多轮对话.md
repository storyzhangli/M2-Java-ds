# D18 技术实现说明与操作实践指南：设备客服与工程师多轮对话

> 适用项目：`E:\AI\project\AI-Learning-two-lp\M2-Java-ds\D18`  
> 技术基线：Spring Boot 3.5.16 / Spring AI 1.1.8 / JDK 21 / MySQL 8.x

## 1. 业务场景与架构

设备链路只负责：

- 收集设备问题和多轮上下文；
- 在信息不足时自然澄清；
- 生成带有不确定性说明的回答；
- 产生只读故障摘要和工单分类候选。

它不负责：

- 正式工单入库；
- 自动建单/派单；
- 伪造知识库引用；
- 替代现场安全人员作诊断或高风险操作许可。

```text
POST /api/v1/equipment/chat
        |
        v
EquipmentChatService
  |-- 校验场景
  |-- 同会话锁
  |-- 校验会话归属
  |-- 读取 COMPLETED 用户消息
  |-- 提取设备事实
  |-- 澄清策略
  |-- PromptTemplateService
  |-- RoleConversationService
  |-- KnowledgeChatOrchestrator
  |-- ChatHistoryService
        |
        v
回答 + 已知事实 + 缺失信息 + 只读候选
```

关键复用：

- Prompt 模板与变量校验；
- MySQL 会话和消息；
- 上下文窗口；
- Mock/DeepSeek 条件装配；
- 真实知识检索与引用清洗。

## 2. Prompt 模板管理

### 2.1 场景

| Scene | 职责 |
|---|---|
| `equipment_customer_service` | 收集设备身份、现象、时间、频率和安全状态 |
| `equipment_technical_engineer` | 整理症状、信息缺口、未验证方向和候选，不替代现场确认 |

场景定义在 `PromptScenes`，角色清单接口会自动返回。

### 2.2 元数据

```json
{
  "templateId": "equipment_customer_service",
  "version": 1,
  "scene": "equipment_customer_service",
  "name": "设备客服场景",
  "description": "制造业设备客服角色...",
  "variables": [],
  "updatedAt": "2026-10-31T...",
  "status": "ENABLED"
}
```

正文通过 `content` 返回。实际项目字段名是 `name`，语义对应需求中的 `templateName`。

### 2.3 变量

| 变量 | 必填 | 用途 |
|---|---|---|
| `known_information` | 否 | 当前由用户原话支持的归纳事实 |
| `missing_information` | 否 | 阻断项和可选缺失项 |
| `business_context` | 否 | 调用方受控背景，不允许伪造引用 |

服务端在渲染前用当前会话事实覆盖同名自动变量，防止客户端篡改“已知信息”。未声明变量仍由既有模板服务拒绝。

### 2.4 版本快照

创建模板：

1. 写当前 `prompt_template`。
2. 写 `prompt_template_version` v1。

更新模板：

1. 归档旧版本快照。
2. 当前行版本 +1 并更新正文。
3. 归档新版本快照。

启动时：

1. `PromptSeedInitializer` 幂等插入缺失种子。
2. `PromptTemplateVersionInitializer` 为存量当前版本补齐快照。

查询：

```http
GET /api/v1/ai/prompts/equipment_customer_service/versions
```

返回最新版本在前；模板逻辑删除后历史快照仍可查询。

## 3. 设备信息抽取

### 3.1 输入边界

只接收：

- 当前会话中状态为 `COMPLETED` 的历史用户消息；
- 当前用户消息。

不把助手回复中的猜测重新当作事实，也不把知识语料内容当作该设备的已确认事实。

### 3.2 规则示例

```text
设备型号 CNC-760
设备编号 A3
报警码 E102
最近运行中异常振动
```

抽取结果：

```json
{
  "deviceModel": "CNC-760",
  "deviceIdentifier": "A3",
  "deviceType": "数控机床",
  "faultCode": "E102",
  "observedSymptoms": ["最近运行中异常振动"],
  "onset": "最近运行中异常振动",
  "currentState": "运行中异常振动"
}
```

“异常振动”是用户原话子句；“数控机床”只来自消息中明确出现的设备类型。

### 3.3 不补全

如果用户只说“设备报警”，系统不会：

- 自选一个型号；
- 编造故障码；
- 虚构传感器读数；
- 声称有维修记录；
- 声称查询了知识库。

## 4. 澄清流程

### 4.1 决策顺序

```text
有没有设备身份？
  否 → 询问型号/类型/编号
  是 ↓
有没有现象？
  否 → 询问报警、异响、振动、温度、停机等
  是 ↓
有没有高风险但安全状态未知？
  是 → 先确认是否停机/断电/隔离
  否 ↓
生成正常回答
```

故障码缺失仍会写入 `missingInformation`，但通常不作为阻断项。提示语是“如有报警码可原样补充”，不会要求用户为不存在的代码编一个值。

### 4.2 多轮示例

第一轮：

```json
{
  "message": "设备运行中一直异常振动",
  "scene": "equipment_customer_service"
}
```

返回：

```json
{
  "clarificationRequired": true,
  "missingInformation": [
    "设备型号或可识别的设备身份",
    "故障码（未提供；如设备有报警码，可原样补充）"
  ],
  "candidateExtraction": {
    "candidateStatus": "NEEDS_CLARIFICATION",
    "deviceModel": null,
    "faultCode": null
  }
}
```

第二轮携带 `sessionId`：

```json
{
  "message": "型号是 CNC-760，仍然有异常振动",
  "scene": "equipment_customer_service",
  "sessionId": "上一轮返回的会话ID"
}
```

系统保留第一轮现象，再合并当前型号，不重复询问型号。

### 4.3 高风险

如果出现“冒烟、带电、高压、带压、高温、高速旋转”等表述，同时安全状态未明确：

- `clarificationRequired=true`；
- 不进入模型正常回答；
- 返回安全确认问题；
- 候选分类为 `SAFETY_RISK`；
- 不提供现场高风险操作步骤。

最终操作仍须遵守现场安全规程并由有资质人员确认。

## 5. 会话 ID 与多轮历史

### 5.1 会话 ID

- 新建会话时服务端生成 UUID 去横线的 32 位字符串。
- 客户端只回传会话 ID，不决定跨用户访问权限。
- 同一会话绑定唯一场景。

### 5.2 Chat Memory 与 Chat History

| 概念 | 本项目实现 |
|---|---|
| Chat History | MySQL `chat_message` 完整消息 |
| Chat Memory | 从 COMPLETED 历史中选最近 N 条形成请求窗口 |
| 默认上限 | 10 条消息，可配置 |

窗口上限是消息条数，不是 Token 预算。

### 5.3 生命周期

- 轮次开始：用户消息 `PENDING`。
- 成功：用户和助手消息 `COMPLETED`。
- 模型异常：用户消息 `FAILED`，不进入后续窗口。
- 流式中断：相关消息 `INTERRUPTED`。
- MySQL 会话跨应用重启保留。
- 清空/关闭继续使用已有历史服务能力。

### 5.4 并发

设备服务对同会话使用固定分段 `ReentrantLock`，覆盖“读取事实 → 准备模板 → 模型调用 → 完成落库”。这使单实例下同会话轮次顺序稳定。

数据库仍保留：

- 会话父行排他锁；
- `(session_id, sequence_no)` 唯一键。

两套机制共同防守并发写入；没有使用静态全局消息集合保存用户对话。

### 5.5 存储选择

当前采用 MySQL，因为 D17 已有完整历史、归属、状态和测试能力。Redis 仍用于模板缓存；旧 `ConversationMemory` 不进入设备主链路。

没有因为本轮需求新增 Redis 会话键或第二套持久化。

## 6. 只读候选 DTO

### 6.1 响应结构

```json
{
  "symptomSummary": "设备运行中一直异常振动；仍然有异常振动",
  "ticketCategory": "MECHANICAL",
  "deviceModel": "CNC-760",
  "faultCode": null,
  "deviceIdentifier": null,
  "observedSymptoms": [
    "设备运行中一直异常振动",
    "仍然有异常振动"
  ],
  "missingInformation": [
    "故障码（未提供；如设备有报警码，可原样补充）"
  ],
  "uncertaintyNote": "当前判断仅基于用户描述，尚未经过现场验证；未提供故障码时不会推测具体代码或根因。",
  "candidateStatus": "CANDIDATE",
  "sourceType": "CONVERSATION_SUMMARY",
  "candidateOnly": true
}
```

### 6.2 分类

| 候选值 | 触发方向 |
|---|---|
| `SAFETY_RISK` | 高风险关键词优先 |
| `THERMAL_COOLING` | 过热、高温、泄漏、流量下降 |
| `MECHANICAL` | 振动、异响、卡滞、过载 |
| `ELECTRICAL` | 跳闸、断电、无法启动 |
| `CONTROL_SENSOR` | 报警、故障灯、位置偏差 |
| `UNCLASSIFIED` | 无足够证据 |

分类只描述候选，不是正式维修结论。

### 6.3 严格 JSON 解析

`EquipmentCandidateParser` 可用于真实模型结构化适配或离线夹具。字段失败时抛出受控参数错误，不把不完整对象写入任何业务表。

推荐正式模型提示词要求：

```text
只输出候选字段 JSON。
缺失设备信息必须为 null。
分类只允许受控枚举。
不得添加根因、维修记录或知识库来源。
```

### 6.4 为什么不会自动写入正式工单

代码边界上：

1. `EquipmentTicketCandidate` 是独立响应 DTO。
2. 没有对应 `@TableName` 或 Mapper。
3. 设备链路没有注入工单 Service。
4. 没有创建、派单和事务写库调用。
5. API 只返回 `candidateOnly=true`。

后续若接入正式工单，应新增显式人工确认命令和权限校验，不能复用候选 DTO 直接写入。

## 7. Mock、DeepSeek 与 Key 安全

### 7.1 默认 Mock

默认：

```yaml
app:
  ai:
    mode: ${AI_MODE:mock}
```

Mock 实现不注入 `ChatModel`，不会访问外网。

设备链路的信息不足澄清也不调用模型，而是确定性规则。

### 7.2 测试隔离

Maven 测试强制：

- `spring.profiles.active=test`
- `app.ai.mode=mock`
- `spring.ai.deepseek.api-key=d01-mock-key-not-for-authentication`
- `AI_MODE=mock`
- 测试环境 `DEEPSEEK_API_KEY` 使用无效占位值
- 在线测试还要 `DEEPSEEK_LIVE_TEST_AUTHORIZED=true`

因此宿主上存在真实环境变量也不会让普通 Maven 测试隐式计费。

### 7.3 安全注入真实 Key

推荐由用户在自己的安全终端中通过环境变量注入，不要把真实值写进命令、脚本、IDE 共享配置或文档：

```powershell
$env:AI_MODE = "deepseek"
# DEEPSEEK_API_KEY 由受控进程环境提供；不要在这里粘贴真实值
mvn -f .\pom.xml spring-boot:run
```

应用配置只引用：

```yaml
spring:
  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY:d01-mock-key-not-for-authentication}
```

默认值显式无效，真实模式下调用前会拒绝占位值。

### 7.4 真实调用授权流程

真实 API 不是 Maven test 的自动步骤。确有必要时：

1. 先完成 Mock 端到端验证。
2. 确认只需验证真实模型兼容性，而不是本地业务逻辑。
3. 向请求方明确模型、接口、脱敏测试输入和可能费用。
4. 获得当前任务的明确授权。
5. 通过安全环境注入 Key。
6. 只发送虚构设备测试数据。
7. 记录调用模式、耗时、状态类别和脱敏结果；不记录 Prompt 正文、响应正文、Authorization 或 Key。
8. 调用结束移除临时环境变量，并复核日志和 Git。

本轮未执行真实调用。

### 7.5 日志

- DeepSeek 服务只记录模型、长度、状态类别。
- 设备接口 `/api/v1/equipment/chat` 从正文访问日志排除。

## 9. 常见问题

### 9.1 返回“当前未检索到可核验的知识来源”

这是预期行为。设备接口默认不检索；没有真实命中时不会构造来源。需要引用时显式设置 `retrieveEnabled=true`，并且只接受检索器真实返回的元数据。

### 9.2 故障码一直缺失

故障码不强制编造。系统会保留“未提供”并继续根据现象形成候选；只有用户确实知道报警码时才建议补充。

### 9.3 同一会话切换客服/工程师被拒绝

这是场景隔离设计。请新建会话。

### 9.4 换用户头后无法访问会话

`X-Dev-User` 是当前开发环境的归属边界，不是生产认证。不同归属不能读取同一 session。生产环境应替换为真实认证主体。

### 9.5 模板更新后旧版本在哪

查：

```http
GET /api/v1/ai/prompts/{templateId}/versions
```

若升级前已有存量模板，启动初始化器会补齐当前版本快照。

### 9.6 测试是否可能产生 DeepSeek 费用

普通 `mvn test` 不会。POM 强制 Mock、占位 Key，在线测试还要求独立授权变量。

### 9.7 日志或 Git 中发现疑似 Key

不要复制或展示值。立即：

1. 停止使用该 Key；
2. 在供应商控制台轮换；
3. 屏蔽日志/报告；
4. 扫描 Git 历史和远程；
5. 经授权清理历史；
6. 重新执行敏感信息扫描。
