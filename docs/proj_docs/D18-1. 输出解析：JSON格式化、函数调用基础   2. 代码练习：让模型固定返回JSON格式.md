## 一、基础概念：模型输出与结构化数据

### 1.1 模型输出的四种基本形式

大语言模型的输出本质上是文本序列，根据约束能力与用途可分为四类：

| 输出形式         | 说明                                      | 业务可用性                             |
| ---------------- | ----------------------------------------- | -------------------------------------- |
| 自然语言文本     | 自由格式的自然语言回答                    | 适合对话、问答，不适合程序直接解析     |
| JSON 文本        | 符合JSON语法的结构化文本                  | 可被程序解析，是业务系统对接的主流形式 |
| 工具调用请求     | 模型生成的工具名称+参数，请求应用执行操作 | 用于扩展模型能力，连接外部系统         |
| 元数据与结束标识 | Token用量、结束原因、使用统计等           | 用于计费、监控、流程判断               |

>
> 核心认知：模型输出默认是**非结构化自然语言**，所有结构化能力都是通过约束、转换、校验多层实现的，不是模型原生就输出Java对象。

### 1.2 JSON 结构基础与常见错误

JSON是结构化输出的基础格式，必须严格区分**语法正确**和**语义正确**两个层次。

#### 合法与非法JSON对比

| 错误类型     | 错误示例              | 正确示例              | 说明                               |
| ------------ | --------------------- | --------------------- | ---------------------------------- |
| 键名无引号   | `{name: "EQ-1008"}`   | `{"name": "EQ-1008"}` | JSON键必须是双引号字符串           |
| 单引号字符串 | `{'name': 'EQ-1008'}` | `{"name": "EQ-1008"}` | JSON字符串必须用双引号             |
| 多余逗号     | `{"a":1, "b":2,}`     | `{"a":1, "b":2}`      | 最后一个字段后不能有逗号           |
| 类型包裹错误 | `{"count": "10"}`     | `{"count": 10}`       | 数字、布尔值不加引号               |
| 前后夹带文本 | `json\n{...}\n`       | 纯JSON字符串          | 模型常输出Markdown代码块包裹的JSON |
| 输出截断     | `{"a":1, "b":`        | `{"a":1, "b":2}`      | 长输出可能被max_tokens截断         |

### 1.3 JSON ≠ 结构化输出：三层校验边界

| 层级     | 校验内容                                 | 作用                 |
| -------- | ---------------------------------------- | -------------------- |
| 语法校验 | 是否是合法JSON格式                       | 保证能被解析器解析   |
| 结构校验 | 字段是否存在、类型是否匹配、枚举是否合法 | 保证能映射为Java对象 |
| 业务校验 | 字段值是否符合业务规则、事实是否有依据   | 保证业务逻辑正确     |

>
> 关键结论：JSON语法正确 ≠ 业务数据有效。模型可能输出语法完全合法，但字段缺失、值越界、事实虚构的内容。

## 二、Spring AI 结构化输出机制

### 2.1 结构化输出完整流程

```
flowchart TD
    A[定义目标Java类型<br/>DTO/Record] --> B[生成格式说明<br/>StructuredOutputConverter]
    B --> C[注入Prompt/模型原生约束]
    C --> D[模型生成文本输出]
    D --> E[输出转换器解析文本]
    E --> F[映射为Java对象]
    F --> G[应用层业务校验]
    G --> H[下游业务使用]
```

>
> 核心机制：Spring AI的结构化输出通过**前置格式引导 + 后置解析映射**共同实现，前者引导模型按格式生成，后者将文本转为Java对象。

### 2.2 ChatClient 核心接口

Spring AI 1.1.x中，结构化输出通过`ChatClient`的流式API调用，核心方法：

| 方法                                          | 作用                         | 返回值         |
| --------------------------------------------- | ---------------------------- | -------------- |
| `call().content()`                            | 获取纯文本响应               | `String`       |
| `call().chatResponse()`                       | 获取完整响应对象，包含元数据 | `ChatResponse` |
| `call().entity(Class<T>)`                     | 将输出解析为指定Java类型     | `T`            |
| `call().entity(StructuredOutputConverter<T>)` | 使用自定义转换器解析输出     | `T`            |

#### 核心示例

```
// 纯文本输出
String text = chatClient.prompt()
        .user("描述设备EQ-1008的故障")
        .call()
        .content();

// 结构化输出，自动解析为Java对象
FaultAnalysis result = chatClient.prompt()
        .user("分析设备EQ-1008的故障描述")
        .call()
        .entity(FaultAnalysis.class);
```

>
> ⚠️ 注意：`.entity()`本质是**文本解析 + 类型映射**，不代表模型一定会严格按结构输出；解析失败会抛出运行时异常。

《Chat Client API | Spring AI 聊天客户端官方文档》：[https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html)

### 2.3 StructuredOutputConverter 接口

#### 定义

结构化输出转换器的顶层抽象，包含两大职责：

1. **格式提供**：生成模型能理解的格式说明，注入Prompt
2. **输出转换**：将模型返回的文本解析转换为目标Java类型

```
public interface StructuredOutputConverter<T> extends Converter<String, T>, FormatProvider {
}
```

>
> 核心特点：它是**尽力转换**机制，成功率依赖模型对格式指令的遵循程度，不能100%保证成功。

《Structured Output Converter | 结构化输出转换器官方文档》：[https://docs.spring.io/spring-ai/reference/1.1/api/structured-output-converter.html](https://docs.spring.io/spring-ai/reference/1.1/api/structured-output-converter.html)

### 2.4 BeanOutputConverter

最常用的结构化输出转换器，用于将模型输出映射为Java Bean或Record。

#### 工作原理

1. 扫描目标Java类型的字段、类型、注解，生成JSON Schema格式说明
2. 将格式说明追加到Prompt末尾，引导模型按结构输出
3. 模型返回文本后，通过Jackson反序列化为目标Java对象

#### 适用场景

- 固定结构的业务数据抽取
- 分类、标签、信息提取任务
- 需要强类型绑定的下游调用

#### 示例类型定义

```
// 设备故障分析结果Record
public record FaultAnalysis(
    String equipmentId,
    FaultCategory faultCategory,
    List<String> knownFacts,
    List<String> missingInformation,
    List<String> recommendedActions,
    Boolean requiresHumanReview
) {}

// 故障分类枚举
public enum FaultCategory {
    ABNORMAL_VIBRATION, OVERHEATING, OTHER, UNKNOWN
}
```

### 2.5 其他内置转换器

| 转换器                | 用途                            | 适用场景                 |
| --------------------- | ------------------------------- | ------------------------ |
| `MapOutputConverter`  | 输出解析为`Map<String, Object>` | 结构不固定、动态字段场景 |
| `ListOutputConverter` | 输出解析为逗号分隔列表          | 简单列表输出场景         |

>
> 注意：`Map`类型牺牲了类型安全，仅建议用于探索性场景；生产环境优先使用明确的Record或DTO。

## 三、固定JSON输出的四种实现方案

### 3.1 方案一：仅通过Prompt约束JSON

#### 原理

完全通过自然语言指令要求模型输出JSON，在Prompt中定义结构、字段、枚举、示例，模型纯文本输出后自行解析。

#### 示例Prompt

```
你是设备故障分析助手。
请根据输入的故障描述，输出JSON格式的分析结果，严格遵循以下结构：
{
  "equipmentId": "设备编号",
  "faultCategory": "分类枚举值",
  "knownFacts": ["已知事实列表"],
  "missingInformation": ["缺失信息列表"],
  "recommendedActions": ["建议列表"],
  "requiresHumanReview": 布尔值
}
枚举值：ABNORMAL_VIBRATION, OVERHEATING, OTHER, UNKNOWN
要求：
1. 只输出纯JSON，不要任何解释、Markdown代码块或额外文字
2. knownFacts只能包含输入中明确提到的事实，禁止编造
3. 无法分类时faultCategory返回UNKNOWN
```

#### 优缺点

| 优点                         | 缺点                           |
| ---------------------------- | ------------------------------ |
| 不依赖框架特性，通用所有模型 | 稳定性差，模型可能夹带额外文本 |
| 灵活，可自定义任意约束规则   | 解析失败率高，需要大量异常处理 |
| 无需额外依赖                 | 字段、类型校验完全靠应用层     |

### 3.2 方案二：Spring AI BeanOutputConverter

#### 原理

通过`BeanOutputConverter`自动生成格式说明并解析输出，是Spring AI推荐的标准结构化输出方式。

#### 调用示例

```
FaultAnalysis result = chatClient.prompt()
        .system("你是设备故障分析助手，只能基于输入事实分析，禁止编造数据")
        .user("设备编号：EQ-1008\n故障描述：运行20分钟后异常振动，面板提示温度偏高")
        .call()
        .entity(FaultAnalysis.class);
```

#### 优缺点

| 优点                     | 缺点                               |
| ------------------------ | ---------------------------------- |
| 框架原生支持，代码简洁   | 仍然依赖模型对格式指令的遵循度     |
| 自动类型映射，强类型安全 | 复杂嵌套结构、枚举可能出现解析偏差 |
| 统一的异常处理机制       | 不支持原生JSON Schema级别的强约束  |

### 3.3 方案三：模型提供方原生JSON模式

#### 原理

调用模型API的`response_format`参数，要求模型严格按JSON格式输出，由模型服务端保证输出语法合法。

#### DeepSeek JSON Output说明

DeepSeek支持通过`response_format`参数指定输出为JSON对象格式，需配合Prompt中的JSON结构说明使用。

#### 接入说明

通过OpenAI兼容接口调用DeepSeek时，可通过模型选项配置`responseFormat`参数。Spring AI 1.1.x的OpenAI实现支持传递响应格式参数。

>
> ⚠️ 注意：原生JSON模式仅保证**语法合法**，不保证字段结构、值范围符合业务要求，仍需应用层校验。

《JSON Output | DeepSeek JSON输出官方文档》：[https://api-docs.deepseek.com/zh-cn/guides/json_mode/](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)

### 3.4 方案四：应用层程序校验

#### 原理

无论模型输出通过哪种方式生成，进入业务逻辑前必须经过程序校验。

#### 校验层级

1. **语法校验**：JSON解析异常捕获
2. **结构校验**：非空校验、类型校验、枚举校验
3. **业务校验**：事实来源校验、业务规则校验、风险等级校验

#### 示例校验逻辑

```
// 1. 解析异常捕获
try {
    FaultAnalysis result = chatClient.prompt()
            .user(input)
            .call()
            .entity(FaultAnalysis.class);
} catch (Exception e) {
    // 解析失败处理
    return FaultAnalysis.unknown(input);
}

// 2. 业务校验
if (result.knownFacts().stream().anyMatch(fact -> fact.contains("编造"))) {
    throw new BusinessException("输出包含未经验证的事实");
}
```

### 3.5 四种方案对比表

| 维度         | Prompt约束       | Spring AI转换器 | 原生JSON模式         | 应用程序校验     |
| ------------ | ---------------- | --------------- | -------------------- | ---------------- |
| 保证级别     | 低，文字约束     | 中，框架引导    | 中高，服务端保证语法 | 最高，程序强制   |
| 依赖模型程度 | 极高             | 中              | 高                   | 无               |
| 实现成本     | 低               | 中              | 中                   | 高               |
| 错误类型     | 格式、结构、业务 | 结构、业务      | 业务                 | -                |
| 适用场景     | 探索性、低风险   | 通用业务场景    | 对格式稳定性要求高   | 生产环境核心链路 |

>
> 推荐组合：**Prompt引导 + Spring AI转换器 + 应用层业务校验**，三层防护，兼顾通用性与可靠性。

## 四、函数调用（Tool Calling）基础

### 4.1 什么是函数调用

函数调用（Function Calling / Tool Calling）是大模型的一种能力：模型根据用户问题，判断是否需要调用外部工具获取信息或执行操作，按约定格式输出工具调用请求，由应用程序执行后将结果返回模型，模型再生成最终回答。

#### 与JSON结构化输出的核心区别

| 维度         | JSON结构化输出           | 工具调用                     |
| ------------ | ------------------------ | ---------------------------- |
| 核心目的     | 返回结构化数据供业务使用 | 请求应用程序执行某项操作     |
| 输出内容     | 目标业务数据             | 工具名称 + 调用参数          |
| 执行主体     | 下游业务直接使用数据     | 应用程序识别并执行对应工具   |
| 是否调用外部 | 否                       | 是，工具执行时调用对应逻辑   |
| 典型场景     | 信息抽取、分类、标签     | 查询数据、执行操作、控制设备 |

>
> 关键边界：模型**只生成工具调用请求**，不实际执行任何方法；所有工具执行、权限校验、错误处理都由应用程序负责。

### 4.2 工具调用完整流程

```
sequenceDiagram
    participant App as 应用程序
    participant Model as 大模型
    participant Tool as 工具方法

    App->>Model: 传入工具定义 + 用户问题
    Model->>App: 返回工具调用请求（工具名+参数）
    App->>App: 校验工具名、参数、权限
    App->>Tool: 执行工具方法
    Tool-->>App: 返回工具执行结果
    App->>Model: 将工具结果传回模型
    Model->>App: 基于工具结果生成最终回答
```

### 4.3 Spring AI 工具调用核心API

Spring AI 1.1.x通过注解式声明简化工具定义，核心接口：

#### 1. @Tool 注解

将Java方法声明为模型可调用的工具。

```
class DeviceTools {

    @Tool(description = "根据设备编号查询设备基础信息")
    public DeviceInfo getDeviceInfo(
        @ToolParam(description = "设备编号") String equipmentId
    ) {
        // 实际业务逻辑
        return new DeviceInfo(equipmentId, "离心泵", "生产车间A");
    }
}
```

#### 2. ChatClient 工具配置

```
// 单次调用注入工具
String response = chatClient.prompt()
        .user("设备EQ-1008的基础信息是什么？")
        .tools(new DeviceTools())
        .call()
        .content();
```

#### 3. ToolContext

工具上下文，用于传递租户、用户权限等应用侧上下文信息，不会发送给模型，仅在工具执行时使用。

>
> 安全关键：工具参数由模型生成，但**执行权限、数据隔离、业务校验必须由应用程序负责**，不能信任模型传入的ID、权限标识。

《Tool Calling | Spring AI 工具调用官方文档》：[https://docs.spring.io/spring-ai/reference/1.1/api/tools.html](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html)

### 4.4 工具参数与JSON Schema

- Spring AI自动根据方法参数生成JSON Schema，描述工具输入格式
- 参数可标注`@ToolParam`补充描述，帮助模型理解参数含义
- 支持必填/可选参数，默认所有参数必填
- 支持基本类型、字符串、数字、布尔、枚举、简单对象

### 4.5 安全边界与错误处理

#### 核心安全原则

1. **权限校验**：工具执行前必须校验用户权限，不能模型说调用就调用
2. **参数校验**：所有输入参数必须经过格式、范围、权限校验
3. **只读优先**：优先实现只读工具，减少副作用风险
4. **幂等设计**：有副作用的工具必须支持幂等，避免重试重复执行
5. **敏感脱敏**：工具参数、结果日志必须脱敏
6. **异常处理**：工具失败时返回明确错误信息，由模型决定如何处理

#### 常见风险

- 越权访问：模型传入其他用户的设备ID，未校验直接查询
- 注入风险：参数包含恶意内容，未校验直接执行
- 重复执行：网络重试导致工具多次执行，产生副作用

## 五、核心知识总结与自测

### 核心总结

1. 模型输出默认是非结构化的，结构化输出是「引导+解析+校验」多层实现的结果
2. Spring AI通过`StructuredOutputConverter`体系提供结构化输出能力，`BeanOutputConverter`是最常用实现
3. 固定JSON输出有四种方案，生产环境推荐「Prompt引导+转换器+业务校验」三层组合
4. 工具调用是模型请求应用执行操作，执行权和安全责任在应用侧
5. 语法正确 ≠ 结构正确 ≠ 业务正确，三层校验缺一不可

> 练习目标：实现设备故障信息的结构化抽取，掌握固定JSON输出、类型映射、多层校验与异常处理

---

## 一、练习目标与业务背景

### 业务背景

制造业设备故障报修场景：用户输入自然语言故障描述，AI自动提取关键信息，按固定结构输出故障分析结果，供后续工单系统调用。

### 核心目标

1. 实现模型输出到Java强类型对象的稳定转换
2. 掌握固定JSON结构的Prompt设计
3. 实现语法、结构、业务三层校验

## 二、输入与输出契约

### 输入示例

```
设备编号：EQ-1008
故障描述：设备运行约20分钟后出现异常振动，随后控制面板提示温度偏高。目前没有提供温度实测值和报警代码。
```

### 固定JSON输出契约

```
{
  "equipmentId": "EQ-1008",
  "faultCategory": "ABNORMAL_VIBRATION",
  "knownFacts": [
    "设备运行约20分钟后出现异常振动",
    "控制面板提示温度偏高"
  ],
  "missingInformation": [
    "温度实测值",
    "报警代码"
  ],
  "recommendedActions": [
    "补充温度实测值及报警代码后进一步分析"
  ],
  "requiresHumanReview": true
}
```

### 字段定义

| 字段                  | 类型         | 约束                                                         | 说明             |
| --------------------- | ------------ | ------------------------------------------------------------ | ---------------- |
| `equipmentId`         | String       | 非空                                                         | 设备编号         |
| `faultCategory`       | 枚举         | 非空，枚举值：`ABNORMAL_VIBRATION`/`OVERHEATING`/`OTHER`/`UNKNOWN` | 故障分类         |
| `knownFacts`          | List<String> | 非空，只能包含输入中明确出现的事实                           | 已知事实列表     |
| `missingInformation`  | List<String> | 非空                                                         | 缺失的关键信息   |
| `recommendedActions`  | List<String> | 非空                                                         | 建议措施         |
| `requiresHumanReview` | Boolean      | 非空                                                         | 是否需要人工复核 |

>
> 强制规则：无法分类时必须返回`UNKNOWN`，禁止编造；knownFacts不得包含输入中没有的信息。

## 四、常见故障排查

| 现象                     | 可能原因                     | 排查方向                               |
| ------------------------ | ---------------------------- | -------------------------------------- |
| 解析异常，提示字段不存在 | 模型输出夹带额外文本/代码块  | 检查原始输出内容，优化Prompt要求纯JSON |
| 枚举值不匹配             | 模型输出非枚举值             | 加强Prompt枚举说明，增加校验降级逻辑   |
| knownFacts包含编造信息   | Prompt约束不足，模型自由发挥 | 强化事实约束，增加业务校验             |
| 输出被截断，JSON不完整   | max_tokens太小               | 调整maxTokens，增加截断异常处理        |
| 工具调用不执行           | 工具未正确注入/描述不清晰    | 检查tools()方法调用，优化工具描述      |
| 同样的Prompt结果不稳定   | 模型随机性、温度太高         | 降低temperature，增加示例约束          |
