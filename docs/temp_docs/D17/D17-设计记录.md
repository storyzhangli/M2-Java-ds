## 1. 设计输入与硬约束

- 技术基线（已核验）：JDK 21（21.0.7）、Spring Boot 3.5.16、Spring AI 1.1.8（spring-ai-bom 锁定，禁升 2.x）、MyBatis-Plus 3.5.17、MySQL 9.7.0（库 `ai_db`，9 张既有表）、Redis 6.2.12、mysql-connector 8.0.33。
- 现状：普通同步链路（无 scene）在 `ChatController` 第 81 行直接 `new ChatInvocation(null, message, List.of())`，**无任何历史关联**；角色链路（带 scene）的历史只存 Redis（`d15f:conv:`，TTL 1800 秒、单会话 20 条 FIFO），**不满足完整持久化与跨重启查询**。
- 硬约束：最小增量；不升级依赖、不引第二套模型链/新中间件；不改 Redis 前缀与既有表结构（新增表走可重复部署迁移脚本 + 回滚说明）；模型 HTTP 调用不得被长事务包围；不 commit。

## 2. 核心概念边界（对应任务书 4.1.1）

| 概念 | 英文全称 | D17 定义 | 落地位置 |
|---|---|---|---|
| 对话历史 | Chat History | 完整、可持久化、可跨重启查询的消息全集，用于展示/审计/恢复 | MySQL：`chat_session` + `chat_message` |
| 对话记忆 | Chat Memory | 仅为当前模型调用选取的有限上下文，不等于历史全集 | `ChatHistoryService.getContextWindow()` 选取最近 N 条 COMPLETED 消息 |
| 会话 | Conversation | 组织消息的业务实体，含归属、场景、状态、时间 | `chat_session` 表与 `ChatSession` 领域模型 |
| 上下文窗口 | Context/Message Window | 允许进入本次模型请求的历史范围，按消息条数控制 | 配置项 `app.ai.history.context-window-messages`，默认 10 |

明确不做：本项目无 Token 计数能力，D17 实现的是**消息条数窗口**，不声称精确 Token 预算；长期语义记忆/摘要压缩不在本次范围。

## 3. Spring AI 1.1.8 API 核验结论与选型

### 3.1 字节码核验事实（证据：D17-javap-memory.txt、D17-javap-advisor.txt）

- `org.springframework.ai.chat.memory.ChatMemory`：接口，方法 `add(String, List<Message>)`、`get(String)`、`clear(String)`。
- `org.springframework.ai.chat.memory.ChatMemoryRepository`：接口，方法 `findConversationIds()`、`findByConversationId(...)`、`saveAll(...)`、`deleteByConversationId(...)`。
- `org.springframework.ai.chat.memory.MessageWindowChatMemory`：final 实现，带 Builder，管理的是**窗口内消息**而非完整业务历史。
- `org.springframework.ai.chat.memory.InMemoryChatMemoryRepository`：进程内 Map 存储，重启即失。
- `org.springframework.ai.chat.client.advisor.MessageChatMemoryAdvisor`：final，实现 `BaseChatMemoryAdvisor`，存在 `before/after/adviseStream` 方法；`after(...)` 在模型返回后把响应自动写入 ChatMemory。
- 本地仓库无 JDBC ChatMemory 构件（未下载对应依赖），且当前主代码使用 `ChatModel` 直连（`Prompt` + `Message`），全工程 grep 确认未使用 `ChatClient`/`ChatMemory`/`Advisor`。

### 3.2 选型决策：业务层手动持久化，不引入 ChatMemory/Advisor

1. 现有链路是 `ChatModel` 直连，引入 `MessageChatMemoryAdvisor` 需先改造为 `ChatClient` 调用链，改动面大且无业务收益。
2. 任务书要求 PENDING/COMPLETED/FAILED/INTERRUPTED 状态机与错误码留痕，Advisor 自动写入只处理成功消息，无法表达失败/中断状态。
3. 双写问题：Advisor 的 `after()` 自动保存 + 业务层手动保存 = 重复保存；D17 仅保留业务层一条写入路径，从结构上规避双写。
4. `InMemoryChatMemoryRepository` 不满足跨重启；JDBC 仓库表结构与本项目状态机不匹配，不引入新依赖。
5. 现有自研 Redis 组件 `ConversationMemory` 保留为 Bean（不删除、不改前缀），但主链路不再调用它写入；其单元测试作为独立组件测试保留。权威存储统一为 MySQL，生产数据不重复落两套存储。

## 4. 数据模型设计（新增两张表，不动既有表）

### 4.1 `chat_session`（会话表）

| 列 | 类型 | 约束/默认 | 说明 |
|---|---|---|---|
| id | BIGINT | AUTO_INCREMENT PK | 代理主键 |
| session_id | VARCHAR(64) | NOT NULL，UNIQUE uk_session_id | 业务会话标识，服务端生成（UUID 去横线） |
| owner_id | VARCHAR(64) | NOT NULL DEFAULT 'dev-user' | 开发归属标识 |
| scene | VARCHAR(64) | NOT NULL DEFAULT '' | 角色场景；普通链路为空串 |
| title | VARCHAR(200) | NOT NULL DEFAULT '' | 首条用户消息安全截断（≤50 字符） |
| template_id | VARCHAR(64) | NOT NULL DEFAULT '' | 角色链路绑定模板 |
| template_version | INT | NOT NULL DEFAULT 0 | 绑定时模板版本，保证可追溯 |
| status | VARCHAR(16) | NOT NULL DEFAULT 'ACTIVE' | ACTIVE/CLOSED |
| created_at | DATETIME | NOT NULL | 创建时间 |
| updated_at | DATETIME | NOT NULL | 更新时间 |
| last_message_at | DATETIME | NOT NULL | 最近消息时间，列表排序用 |

索引：`uk_session_id`；`idx_owner_status(owner_id, status, last_message_at)`。

### 4.2 `chat_message`（消息表）

| 列 | 类型 | 约束/默认 | 说明 |
|---|---|---|---|
| id | BIGINT | AUTO_INCREMENT PK | 代理主键 |
| session_id | VARCHAR(64) | NOT NULL | 所属会话业务键 |
| owner_id | VARCHAR(64) | NOT NULL | 冗余归属，便于清理与隔离校验 |
| sequence_no | INT | NOT NULL | 会话内单调递增，从 1 开始 |
| role | VARCHAR(16) | NOT NULL | user/assistant；system 消息不持久化（系统提示词由模板实时渲染） |
| content | TEXT | NOT NULL | 消息正文 |
| status | VARCHAR(16) | NOT NULL | PENDING/COMPLETED/FAILED/INTERRUPTED |
| model_name | VARCHAR(64) | NOT NULL DEFAULT '' | 产出该消息的模型名 |
| error_code | VARCHAR(32) | NOT NULL DEFAULT '' | 失败/中断错误码 |
| error_message | VARCHAR(500) | NOT NULL DEFAULT '' | 安全错误摘要（不含堆栈/密钥） |
| created_at | DATETIME | NOT NULL | 落库时间 |
| updated_at | DATETIME | NOT NULL | 状态变更时间 |

索引：`uk_session_sequence(session_id, sequence_no)`；`idx_session_status(session_id, status, sequence_no)`。
不建物理外键（沿用项目 `prompt_template` 无外键 + 应用层校验的既有风格）；不依赖 created_at 排序，同毫秒消息由 sequence_no 保证稳定顺序。

### 4.3 序号生成与并发顺序

- 短事务内 `SELECT MAX(sequence_no) ... FOR UPDATE` 锁定该会话行序列，取 `max+1` 后 INSERT，立即提交。
- 同一会话并发请求因此被串行化，消息顺序确定；`uk_session_sequence` 作为最后兜底，冲突时抛错并失败留痕，不静默重复。
- 重复提交（T11）口径：无客户端幂等键时，同一内容重复请求按新消息处理（语义现实，文档明示）；同事务内重试受唯一约束保护不会产生重复行。

### 4.4 阶段 D 实测更正：并发方案的两次演进（真实失败留痕）

> 本节为阶段 D 真机/全量测试后的设计更正，替代 4.3 中「消息表 FOR UPDATE」的原始口径；代码 Javadoc 已同步，失败证据保留在 temp_docs/D17。

**演进一：消息表 `SELECT MAX ... FOR UPDATE` → InnoDB 1213 死锁（D17-full-test3.txt）**

- 现象：8 线程并发同会话，7 个抛 `DeadlockLoserDataAccessException`（MySQL 错误 1213），异常点为消息表锁定读。
- 机理：`uk_session_sequence` 复合索引下，多事务对同一会话间隙做锁定读，先拿到间隙锁（Gap Lock）；随后 INSERT 需要的插入意向锁（Insert Intention Lock）与其他事务持有的间隙锁互斥，形成锁等待循环，InnoDB 自动选择牺牲者回滚。
- 决策：串行化手段改为对父表 `chat_session` 已存在的唯一记录执行 `SELECT id ... FOR UPDATE`（记录锁，不产生间隙锁），消息表 MAX 改为普通 SELECT。

**演进二：父行锁未串行 → REPEATABLE READ 旧读视图（D17-full-test4.txt）**

- 现象：死锁消失，但 7 个线程 INSERT 时抛 `DuplicateKeyException`（重复键 `<sessionId>-3`），即多个 startTurn 都读到 MAX=2。裸 JDBC 同构探针（LockProbe）证明数据库层 FOR UPDATE 阻塞正常（T2 等待 3003ms），Spring 环境诊断（SpringLockDiagnosticTest）证明编程式事务与声明式事务的锁阻塞均正常。
- 根因：原 startTurn 先执行 `requireOwnedSession` 的普通 SELECT（建立 REPEATABLE READ 一致性读视图），再执行父行 FOR UPDATE。锁等待结束后，同事务内的普通 MAX 仍基于**锁前建立的旧视图**，读不到并发事务已提交的新序号。
- 最终决策（已落地）：父行锁必须是写事务内**第一条语句**，先于任何一致性读——已有会话先锁后查，新会话先插入父行再锁；`completeTurn`/`interruptTurn` 方法首句即锁，天然满足。修复后并发测试通过，全量 121 用例 0 失败（1 个 LiveSmoke 无 Key 按设计跳过）。

## 5. 上下文窗口策略

- 配置：`app.ai.history.context-window-messages`，默认 10，环境变量 `AI_CONTEXT_WINDOW_MESSAGES` 覆盖。
- 取数：`session_id=? AND status='COMPLETED'`，按 sequence_no DESC LIMIT N，再反转为正序。
- 轮次完整性：若窗口首条为 assistant（孤立回复），向前补一条对应 user，避免截断破坏问答轮次。
- 组装顺序：SystemMessage（角色模板实时渲染）→ 窗口历史（user/assistant 交替）→ 当前 UserMessage（只加入一次）。
- 首轮新会话历史为空，按单轮处理；不同 session_id 之间不共享任何上下文。

## 7. 链路改造与事务边界

### 7.1 同步链路（ChatController）

1. `startTurn`（独立短事务，提交后再调模型）：打开/获取会话 → 写入 PENDING 用户消息。
2. 读取上下文窗口 → 组装 `ChatInvocation` → `KnowledgeChatOrchestrator.chat`（模型调用在事务外）。
3. 成功 `completeTurn`（短事务）：用户消息 PENDING→COMPLETED；插入 COMPLETED 助手消息；更新会话 last_message_at。
4. 失败 `failTurn`（短事务）：用户消息→FAILED 并记录 error_code/error_message；不伪造助手成功消息。

### 7.2 流式链路（ChatStreamController）

- 流开始前：PENDING 用户消息落库（短事务提交）。
- 流过程中：助手内容仅内存累积，不逐 chunk 写库。
- 正常 complete：用户消息 COMPLETED + 助手 COMPLETED 全文落库。
- error/timeout：`failTurn`；客户端断开/手动停止且已有部分内容：助手消息 INTERRUPTED（保留部分正文），用户消息标记 INTERRUPTED；无任何内容时按失败处理。

### 7.3 角色链路（RoleConversationService）

- 保留：模板状态校验、系统提示词渲染、`PreparedConversation` 对外形态。
- 替换：会话绑定、历史组装、消息读写全部委托 `ChatHistoryService`（携带 scene/template_id/template_version），不再调用 `ConversationMemory`。
